# Design

## Context

动机见 `proposal.md - Why`。行为契约见 `specs/document-chunking/spec.md`。

影响设计的三条现状约束（均已核对源码）：

1. **切分逻辑在库内，且不可参数化选择。** `hello_agents/memory/rag/pipeline.py` 的
   `load_and_chunk_texts` 恒走 Markdown 结构感知一条路径（源码注释直言
   "Always use markdown-aware chunking for better structure preservation"），
   `RAGTool._add_document` 只透传 `chunk_size` / `chunk_overlap`，没有策略入口。
   该库位于 `site-packages`，非本项目代码。

2. **入库有硬性元数据契约。** `search_vectors` 的过滤条件是四个字段同时命中：
   `memory_type == "rag_chunk"`、`is_rag_data == True`、`data_source == "rag_pipeline"`、
   `rag_namespace == <ns>`。缺任意一个，chunk 在检索中**静默不可见**——不报错，只是搜不到。
   这四个字段由 `index_chunks` 在写入时自行注入。

3. **现有预览是入库后回读。** `11_Q&A_Assistant.py` 的 `get_chunks_visualization` 经
   `_get_chunks_from_qdrant` 从 Qdrant scroll 出结果。预览与入库是两条路径，
   且预览必然发生在入库之后。

## Goals / Non-Goals

**Goals:**

- 预览与入库共用同一份数据，二者不可能不一致
- 三种策略共享统一的内部契约，新增策略只增加一个切分器
- 语义分割的参数调节具备交互性（拖动滑块不触发重新向量化）
- 换策略重新入库后知识库中不留旧 chunk
- 已入库文档不受本次变更影响，无需数据迁移

**Non-Goals:**

- 不修改 `hello_agents` 库（不 monkeypatch、不 fork、不 vendor）
- 不引入第三方切分框架（langchain-text-splitters 等）
- 不做多策略并排对比视图
- 不做 chunk 的手工编辑/合并/删除
- 不改动检索与排序算法

## Decisions

### D1：切分逻辑上移到应用层，不改库

**选择**：应用层自行完成「转换 → 切分 → 物化」，然后直接调用库的公开入库入口。

**备选与否决理由**：

| 方案 | 否决理由 |
|---|---|
| 给库打补丁 / monkeypatch | 改 `site-packages`，重装即失效，对教学项目是隐性陷阱 |
| 在 `sys.path` 前置一份库的副本（vendoring） | 副本会与上游漂移，学习者调试时看到的是副本而非真实库 |
| 向上游提 PR 加策略参数 | 反馈周期不可控，且本次是本地教学项目，不该被外部依赖阻塞 |
| **应用层自切（选中）** | 切分策略成为本章可读、可改、可调试的代码；库退化为「转换 + 存储」两个职责 |

**代价**：应用层必须自行满足第 2 条约束。缓解见 D2。

### D2：入库只走 `index_chunks`，不走 `store.add_vectors`

`index_chunks(store, chunks, rag_namespace=...)` 是库的公开入口，它自己注入那四个
过滤标签，并统一做 embedding 预处理。直接调 `store.add_vectors` 需要手工复刻这四个
标签，漏一个就是静默失效。

**结论**：应用层只负责产出 chunk dict，「加标签」这件事永远交给 `index_chunks`。
这是一个单点决策，换来了对最危险失效模式的免疫。

### D3：单一漏斗——预览与入库消费同一个 list

```
  文件 (pdf/docx/mp3/png/...)
       |
       v   markdown 提取 (带缓存)
    markdown 原文  ──────────────> start/end 的坐标系
       |
       v   splitter(md, params) -> (chunks, diagnostics)
    Chunk[]  { content, start, end, heading_path }
       |
       v   materialize(chunks, path, namespace)     <-- 唯一物化点
    可入库 dict[]  (id + content + metadata)
       |
       +---------------------+---------------------+
       |                                           |
       v                                           v
  渲染预览 (HTML/曲线)                    index_chunks(store, dicts)
       |                                           |
       +------> 使用者据此决定是否入库 <-----------+
                （同一个 list 对象，非"等价结果"）
```

`materialize` 之下只有一条路径，预览漂移在结构上不可能发生。

### D4：切分器统一接口与策略注册表

每个策略实现同一签名：

```
split(markdown: str, params: dict) -> (chunks: List[dict], diagnostics: dict)
```

- `chunks[i]` = `{ content, start, end, heading_path }`，`start`/`end` 为 markdown 原文真实字符偏移
- `diagnostics` 承载策略特有的可视化数据（语义分割在此返回切点距离序列）

**不变量一：非空白字符必须被完整覆盖。** 偏移自洽（`markdown[start:end] == content`）
并不蕴含内容完整——中间的整段漏掉时，每一块的偏移依然各自成立。所以模块内另有两条
约定，并由覆盖检查兜底：

- 标题行的文字进入其后那一块的 `content`（不只是记进 `heading_path`）。章节标题往往
  是整块里最容易被检索命中的一段文字，丢掉它就等于这块内容匹配不到「关于某一章」的提问。
- 装填循环换块时，触发换块的单元必须成为新块的第一员。漏掉它，每个单元都会被下一次
  换块顶掉，文档被静默丢内容。

**不变量二：`chunk_size` 是硬上限，重叠必须让路。** 上面第二条是把重叠和新单元放进
同一块，所以补上它之后必须复查预算——少了这次复查，重叠就能把块顶出上限（默认参数下
800 会变成 822，且这条路径正是「🏠 开始使用」的一键加载）。带上重叠装不下这个单元时，
这一处边界就不带重叠。两条不变量会互相拉扯：保住内容的那一步必须同时保住尺寸，
否则只是把一个 bug 换成另一个。

**库的写法不能照抄**：库的 `_chunk_paragraphs` 换块时不推进下标，下一轮拿同一段落重判
预算，因此不超限——但它会产出纯重叠块，且当被保留的重叠后面跟着一个
`> chunk_size - overlap` 的段落时**死循环**（每轮重新 emit 同一个纯重叠块，永不推进）。
所以这里取「丢弃该次重叠」，而不是「重新判定」。

注册表把策略名映射到 `{ 切分器, 参数规格 }`。参数规格描述该策略的控件（名称、类型、
范围、默认值、单位），UI 据此动态生成参数面板——因此「切换策略时参数面板随之变化」
是注册表的自然结果，而不是每个策略写一遍 UI。

### D5：语义分割算法

```
① 原子单元切分
   句子级原子（。！？；+ 换行 + 空行）
   围栏代码块与表格整体视为一个原子  <-- 否则代码里的标点会把代码切碎

② 原子向量化
   对第 ① 步产出的原子文本，先做与入库相同的 markdown 预处理，
   再用与入库相同的 embedder 批量编码    <-- 保证距离反映真实入库向量

③ 相邻距离
   d[i] = 1 - cos(v[i], v[i+1])

④ 切点判定
   tau = percentile(d, 100 - P)     P 即界面「语义敏感度」
   在 d[i] > tau 处切

⑤ 尺寸兜底（不可省）
   合并 < min_chars 的碎块；拆分 > max_chars 的巨块
   合并会吃掉一部分候选切点，因此 ⑥ 报出的切点是**兜底之后实际成为
   chunk 边界的那几处**，另附被合并的候选数量供界面说明原因

⑥ 产出 chunks + 切点距离序列与阈值（供可视化）
```

**分位数的方向**：敏感度越高 → 分位越低 → 阈值越低 → 更多断点被判为切点 → chunk
越多。写成 `100 - P` 而不是 `P`，是因为「敏感度」的直觉是「越高越容易判定转折」，
而分位数越大阈值越高、切点越少，两者方向相反。spec 要求「敏感度越高，产生的切分
点越多」，此处以 spec 为准。

**为什么用分位数而非绝对阈值**：绝对阈值对文档敏感——同一阈值换一份文档就完全失效
（或切得粉碎，或一处不切）。分位数让「敏感度 75」在任何文档上都表示同一个相对含义
（切在距离高于 25% 分位处），参数可跨文档迁移。这也是滑块能有意义地标成百分比的原因。

**为什么 ① 要保护代码块/表格**：它们在语义上是一个不可分的整体，被切开后
既产生无意义的向量，也在展示时割裂内容。

### D6：原子向量缓存是交互性的前提

② 是全流程唯一昂贵且需要网络的步骤。按 `(markdown 内容哈希, 原子切分参数)` 缓存
原子向量后，拖动敏感度滑块只重跑 ④⑤⑥——纯 Python 数组运算，无需再访问模型。

没有这层缓存，「语义敏感度」滑块每动一次就要重新编码全文，功能实际不可用。

**配套**：Gradio 滑块用 `.release()` 而非 `.change()` 触发，避免拖动过程中的中间值
触发连续重算。

### D7：距离曲线是语义分割的必要可视化

卡片列表能展示「切成了什么样」，但无法解释「为什么在这里切」。语义切点是算出来的，
使用者看不到依据就无法建立对参数的直觉。因此语义策略额外渲染：

```
  相邻原子距离 d[i]
 1.0 |                    *
     |                   * *
 0.6 |        *         *   *        *
     |   *   * *   *   *     *   *  * *
 0.3 |  * * *   * * * *       * * * *
     | *                              *
 0.0 +----------------------------------> 原子序号
         ^           ^            ^
        切          切           切
     - - - - - - - - - - - - - - - - -  tau = percentile(d, 100 - P)
```

拖动敏感度 → 虚线上下移动 → 切点增减，参数的作用立刻可见。

**标记的是实际边界，不是候选点**：⑤ 的尺寸兜底会合并掉一部分候选切点。若曲线上
标候选点，会出现「十几个红点、结果只有一块」这种看不懂的图，使用者会以为滑块失灵。
所以曲线只标真正成为 chunk 边界的那几处，被合并的数量另行说明（尺寸约束所致）。

其余两个策略不产出距离序列，`diagnostics` 为空时该区块不渲染——这是 D4 统一接口
的自然结果，UI 无需为策略分支。

### D8：重新入库 = 先清旧、再写新

```
   ① 本地切分 + materialize            <-- 先做，失败时数据库毫发无伤
   ② scroll 出 source_path == file_path 且 rag_namespace == <ns> 的旧 point id
      （复用现有的 scroll 分页写法，只是这次只要 id）
   ③ delete_vectors(old_ids)
   ④ index_chunks(store, new_dicts)
```

顺序关键在 ① 先于 ②：切分失败（格式不支持、embedding 不可用）时不会留下已删除的文档。

**② 必须带上 `rag_namespace`。** 集合是所有命名空间共享的（见上文「入库有硬性元数据契约」），
只按 `source_path` 过滤时，同一路径的文件被两个身份各自入库会互相取到对方的 point——而本步
是删除路径的前置枚举，会**删掉对方的数据**。这条漏了会形成一个 spec 措辞看不出来的盲区：
受影响的那份与被清理的这份**同路径**，按「不得影响知识库中其他文档」的字面读不出来。

**②③④ 之间非原子**，中途失败会导致该文档从知识库消失。取舍：

| | 做法 | 代价 |
|---|---|---|
| **选中** | 明确报错「该文档需重新入库」 | 使用者需手动重试 |
| 备选 | 删前把旧 point 暂存，失败时回滚 | 复杂度显著上升 |

否决回滚方案的理由：这是跑在本机 Qdrant 上的教学项目，失败窗口极窄（向量已在 ① 之外
算好），为它引入事务语义的复杂度不值当。对应 spec 中「入库失败时报告失败」的
MUST NOT 静默成功要求。

`doc_id` 只依赖 `(path, markdown 长度)`，因此换策略不改变 `doc_id`；
`chunk id` 依赖 `(doc_id, start, end, content_hash)`，换策略必然改变，这正是必须清理旧 chunk 的原因。

### D9：文件划分——拆出新模块

`11_Q&A_Assistant.py` 已 1196 行。切分器 + 渲染器预计再增 400–500 行，全部内联会
让该文件难以阅读，且切分逻辑与 UI 耦合后无法单独测试。

**选择**：

| 文件 | 职责 |
|---|---|
| `chunking.py` | markdown 提取（包一层私有函数）、三种切分器、策略注册表、原子向量缓存、`materialize` |
| `chunk_viz.py` | 纯渲染函数：chunk 卡片、距离曲线、尺寸分布；输入 chunk 列表，输出 HTML |
| `11_Q&A_Assistant.py` | 仅保留 UI 接线与 Gradio 回调 |

**代价**：chapter8 现有 `01_`~`11_` 全部是互不 import 的单文件脚本，这会是本章第一次
跨文件导入。属有意为之——切分逻辑值得独立成模块，且无数字前缀的文件名本身就把它
与「按顺序学习的章节脚本」区分开。

**渲染器共用**：现有 `get_chunks_visualization` 拆为「取数」与「渲染」两半，
`chunk_viz.py` 只保留渲染。切分工作台的本地预览与「查看文档切分」的 Qdrant 回看
共用同一个渲染函数，因此入库后回看的能力不丢失。

### D10：参数单位诚实标注

库的 `_approx_token_len` 表明 `chunk_size` 的计量是 **token**（CJK 字符按 1 计，
非 CJK 按空白分词计），而现有界面将其标注为「字符」（`11_Q&A_Assistant.py` 内两处：
参数条与文本模式摘要）。

**选择**：统一按 token 计量并标注为 token；同时另行展示每个 chunk 的实际字符数
（现有卡片已有该字段，是真字符数，保持不变）。两者并存不冲突，因为标签诚实。

**备选**：改为按字符切分。否决——会让本应用的切分行为与库的默认行为不一致，
且 `chunk_size=800` 这一沿用值在字符语义下含义完全不同，改的是行为而非标签。

### D11：预览失效用参数指纹判断

预览时记录指纹 `(file_path, markdown 内容哈希, 策略名, 参数字典)`，随预览结果一起保存。
提交入库前比对当前指纹与保存的指纹：不一致则拒绝入库并要求重新预览。

指纹包含 markdown 哈希，因此重新上传同名但内容不同的文件也会使预览失效。

### D12：markdown 提取加缓存

`_convert_to_markdown` 对 PDF / 音频 / 图片是昂贵操作（含 OCR / 语音转写）。
按 `(file_path, mtime, size)` 缓存提取结果，使使用者切换策略、反复调参时不必重复提取。

该函数是模块级私有（下划线前缀）。包一层适配器，导入失败时回退到
`_fallback_text_reader`，使库升级改名不至于让整个工作台不可用。

### D13：嵌入请求由应用层分批，入库后回读核对

库的 embedding REST 调用把读超时写死为 30 秒（`embedding.py` 里
`requests.post(..., timeout=30)` 是字面量，不是配置项），而 `index_chunks` 默认按
**64 条一批**发送。本机 Ollama 编码 64 条中文长块远超 30 秒，必然超时。

**超时本身还不是最糟的。** `index_chunks` 的「小批次重试」分支对 `encode()` 返回的
`list[ndarray]` 判断错误——它把整批当成单条向量，于是异常被吞掉，每 8 条只补 1 条
零向量就继续。零向量对任何查询的余弦相似度都是 0，永远检索不到；数量又对不上
metadata，`add_vectors` 按 `zip` 配对，以最短者为准，多出来的 chunk 被静默丢弃。
最后它仍打印 upsert 成功——不抛异常、不报错。

**选择：**

1. **自己控制请求大小。** 入库传 `batch_size=EMBED_BATCH_SIZE`（8）；原子编码用
   `_batch_by_chars` 按字符预算分批（原子大小悬殊，整个代码块是一个原子，只按条数
   管不住）。待在 30 秒以内，就不必依赖那个坏掉的回退分支。

   8 这个值是量出来的：本机实测（每块约 2700 字符，nomic-embed-text）
   `batch=8 → 13.3s`、`batch=16 → 27.0s`、`batch=32 → 30.0s 读超时`（正是使用者
   那次报错）。吞吐约 1600 字符/秒且基本线性，故减小批次几乎不损失总耗时。
   使用者那份 PDF 实测 1983 字符/块，取 8 约 10 秒，留 3 倍余量。
2. **入库后回读核对。** `index_document` 写完后按 `source_path` + `rag_namespace` 数一遍
   实际条数，与 `len(materialized)` 不符即抛 `IndexingError`。`index_chunks` 在这条路径上
   不抛异常，我们的 `except` 等不到，只能自己查。带上命名空间是必须的：跨命名空间计数会让
   这个校验失真——既可能假通过（别处的 chunk 补齐了缺口），也可能假失败。

第 2 条是第 1 条的兜底：分批只是避开触发条件，没有消除降级的可能——Ollama 只要再慢
一次，同一条路还会走通。这正是 D8 承诺的「不静默成功」，只是要靠回读才兑现得了。

**代价**：每次入库多一次 scroll（一次轻量读）。相对「一份残文档冒充入库成功」不值一提。

### D14：读路径显式传 namespace

库的 `RAGTool.run(parameters)` 在分派 `ask` / `search` / `stats` / `clear` 时，namespace 取
`parameters.get("namespace", "default")`——**默认值 `"default"` 是写死的字面量，与构造时传入的
`rag_namespace` 无关**，`_get_pipeline("default")` 会另建一条命名空间为 `default` 的管道。
本应用写入用 `docs_{user_id}`，读路径原先不传 namespace，于是**写 `docs_yyh`、读 `default`**：
问答检索到的是 `default` 下那份无关文档，且不报错。

这与第 17 行那条「缺任一标签则静默不可见」是同一类失效的两种形态：那边是**什么都搜不到**，
这边是**搜到了别处的文档**——后者更糟，因为返回的是一份看起来完整的答案。

**选择**：加一个 `_rag()` 漏斗，所有读操作统一
`setdefault("namespace", self.rag_tool.rag_namespace)`，调用点不再直接碰 `rag_tool.run`。
回看路径同理：`_get_chunks_from_qdrant` 的 scroll 过滤只按 `source_path`，一并补上
`rag_namespace`。

**否决给库打补丁**：`parameters.get("namespace", "default")` 是库的公开签名行为，不是缺陷；
应用层显式传参即可，符合 D1/D2。

**顺带让状态可见**：`init_assistant` 报告实际使用的命名空间与其下 chunk 数，空命名空间时
明确提示。这类故障之所以难发现，正是因为读错命名空间**不产生任何错误信号**，只能把实际
读写的位置摆到使用者眼前。

## Risks / Trade-offs

- **契约漂移**（应用层 chunk 缺过滤标签 → 检索静默失效）→ 只走 `index_chunks`（D2），
  并由 spec 的「入库 chunk 保持可检索」场景验收
- **`start`/`end` 偏移不准** → 不会崩溃，但会静默劣化
  `compute_graph_signals_from_pool`（1600 字符近邻窗口）与 `expand_neighbors_from_pool`
  的效果，是最难排查的一类问题 → 各切分器均从原文切片位置回填偏移，不用估算值；
  验收时以「chunk 内容 == markdown[start:end]」为断言
- **删旧与写新之间非原子** → 明确报错，不回滚（D8）
- **语义分割的模型成本** → 原子向量缓存（D6）；若 embedding 服务不可用，
  语义策略应报错并提示改用其他策略，而非静默退化
- **embedding 服务慢导致的静默降级** → 这是最难发现的一类失败：库在编码超时后
  塞零向量并照常返回成功，chunk 既不报错也检索不到 → 应用层分批 + 入库后回读
  核对（D13）
- **超长段落产出巨块** → 段落分割与 Markdown 策略均须有最大块兜底（spec 已要求）
- **依赖库的私有函数** → 适配器 + 回退路径（D12）
- **文件规模与章节惯例** → 拆模块（D9），代价是打破单文件惯例
- **语义分割的原子切分依赖标点** → 对无标点的长文本（如某些 OCR 结果）原子会退化为
  整段，此时语义分割退化为「按块大小切」。这是可接受的降级，但需在 UI 上提示

## Migration Plan

**无需数据迁移。** 已入库文档的 chunk 元数据是本次新增元数据的子集，检索路径不变。

**部署**：新增 `chunking.py` / `chunk_viz.py`，改造 `11_Q&A_Assistant.py`。
无 collection 重建、无 schema 变更、无新服务依赖（复用现有 Qdrant 与 embedding 配置）。

**回滚**：还原 `11_Q&A_Assistant.py` 并删除两个新模块即可。经新流程重新入库过的文档
仍是合法 chunk（元数据为超集），无需回滚数据。

**建议验证顺序**：
1. 用一份已入库文档走默认快速路径，确认原有行为未变、检索仍正常
2. 同一文档走切分工作台，用 Markdown 策略入库，确认 chunk 数与预览一致
3. 换段落分割再入库，确认旧 chunk 已被清除、其他文档不受影响
4. 用语义策略调整敏感度，确认曲线与切点数联动、拖动流畅
5. 就新入库文档提问，确认检索命中
