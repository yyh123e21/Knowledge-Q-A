# Design

## Context

见 `proposal.md` — Why：动机与实测证据不在这里重述。

设计前必须先知道的三件事，全部是本次实测的结论，它们决定了整个方案的形状：

1. **`extract_markdown()` 不保留页界。** 对封思敏那份 PDF，返回 163,545 字符，其中换页符 `\f`
   0 个、HTML 注释 0 个、页码标记 0 个。题注在文本层里已被拆碎成 `MLRA 算法框架如图` /
   `2－5 。` 两行——所以「按页把描述缝回平坦正文」不存在可靠的锚点。

2. **`_protected_regions()` 只被语义分割消费。** 全仓库只有一处调用点（`chunking.py:1005`，
   在 `_iter_atoms` 内）。段落分割与 Markdown 分割不经过它——它们按空行与标题切，所以一个
   自成一段的视觉块在它们那里天然不会被切开；只有语义分割会按向量距离在块内部切断。

3. **`preview_fingerprint()` 里含 `markdown_hash`**（`chunking.py:1476`），而 `is_fresh()`
   会重新提取一次文本再比指纹（`chunking.py:1709`）。这意味着只要 T′ 确实随视觉配置变化，
   「参数变化后预览失效」这条既有契约**由构造保持**，不需要改它。

## Goals / Non-Goals

**Goals:**

- PDF 的每一页与独立图片文件，其图上的可读信息成为可切分、可入库、可检索的文字。
- 视觉提取的失败逐页可见，且不出现「失败的页报告成功」。
- 一次提取的代价只付一次：落盘、可续跑、同一配置下逐字可复现。
- 不新增第二条提取路径——预览与入库继续消费同一份文本。

**Non-Goals:**

- 不做版面分析（一页里有几个子图、图注归属、阅读顺序）。见 proposal 的 Non-goals 3。
- 不改清洗的三类定点改动，不用 `NFKC`。见 proposal 的 Non-goals 1。
- 不动存量 chunk，不做自动重切。见 proposal 的 Non-goals 4。
- 不追平 `pypdf` 嵌入图镜像那条路线。见 proposal 的 Non-goals 5。
- 本设计不覆盖 `.docx` / `.txt` / `.md` / `.csv` 等文本格式——它们不进入视觉段。

## Decisions

### D1. 合并点放在 `_extract_record()` 内部

**选择**：视觉段的产出与页面文本的合并发生在 `chunking.py:140` 的 `_extract_record()` 内，
在 `_convert_via_library()` 之后、`assess_extraction_quality()` 之前，产出合并文本 T′。

**被否决的替代方案**：在 `Workbench.preview()` 与 `index_document()` 两处分别注入视觉文本。

**否决理由**：那会让「预览=入库」从一条构造性事实退化成一条需要人工维护的同步关系。
`_extract_record` 是唯一提取入口（`chunking.py:181` 的 `extract_markdown()` 是它的门面），
预览（`chunking.py:1686`）、入库（`chunking.py:1749`）、`is_fresh`（`chunking.py:1709`）
三个调用点自动全覆盖；两处注入则要保证两条路径拼出的 T′ 逐字相同，而它们本来就会各自漂移。

**代价**：`_extract_record` 成为全项目唯一同时依赖视觉模块的地方，它必须能在视觉不可用时
整体跳过并保持原有行为（见 D10）。`chunking.py` 因此多了一个模块级依赖，与其「所有算数的
逻辑都在这」的定位一致，但会让该文件的导入图多一条边。

### D2. 正文来源用视觉整页转写（缝法 B）

**选择**：PDF 的 T′ 由逐页整页渲染后交给视觉模型转写得到，视觉模型的转写**就是**该页的正文。

**被否决的替代方案 A**：只把图的描述缝回正文，正文仍用库的提取结果（缝法 A）。

**否决理由 A**：`extract_markdown()` 不保留页界（Context 1），插入点只能靠在平坦正文里
`str.find` 一段特征串来猜；而题注已被拆碎成 `MLRA 算法框架如图` / `2－5 。`，正文里还混着
图内 OCR 文本，锚定失败不是边缘情况而是常态。缝法 B 的页界**由构造保证**——页面是我们自己
逐页渲染的，不需要从平坦文本里反推。

**被否决的替代方案 B**：用 `pypdf` 抽嵌入图后单独送模型（路线甲）。

**否决理由 B**：已实测 `.images[i].image` 不含 PDF 的放置变换矩阵，第 31 页 1823×860 的插图与
第 50 页的框图文字全是水平镜像的。整页渲染天然没有这个问题。

**代价**：引入「模型漏字则该内容从知识库消失」的新风险。这不是可以靠设计消除的风险，只能靠
D7 的对照呈现让它可见——而且**误报会让这条信息失去可信度**，所以对照只呈现、不判定。

### D3. 渲染比例 1.5，模型 `qwen3-vl-235b-a22b-instruct`

**选择**：整页渲染 scale = 1.5（A4 约 819×1243，1.02 MP）；模型走 `.env` 的 `VLM_MODEL_ID`，
当前值为 `qwen3-vl-235b-a22b-instruct`。

**数字怎么量出来的**：同一句「由于卫星路由问题具有离散低维动作空间特性…」在不同有效比例下
送同一批模型：scale 0.8（0.03 MP 的段落测试）时 235B 读成「高维低维动作空间特性」；
scale 1.5 与 3.0 时逐字正确。云端 single-page 实测：scale 1.5 下 235B 为 16.5–18.1 s，
`qwen3-vl-flash` 为 9.6 s。取 1.5 是实测的准确率拐点，不是折中值。

**被否决的替代方案**：`qwen3-vl-flash`（快 1.7 倍）。

**否决理由**：低分辨率单样本上它反而更准（同一段 0.027 MP 文本它读对了「离散」，235B 读错），
但样本量不足以判定；而 235B 已在正确定向的插图、低分辨率段落、曲线图三条判据上验过，
其中曲线图的描述经逐条比对渲染页无一处编造。在一个「错一个字就静默污染知识库」的场景里，
用样本量不足的证据去换 1.7 倍速度不划算。

**代价**：单份 70 页约 19 分钟（原速约 11 分钟）。本机 CPU 跑同一件事要 1.4–6 小时
（实测 140 s/百万像素且线性），所以这个代价是相对于「不可用」而非「可用」而言的。

### D4. 落盘缓存：每页一个文件，键含配置指纹

**选择**：`.chunk_cache/<文件指纹>/<配置指纹>/` 下每页一个 JSON（`page-0005.json`）；
文件指纹那一层另存 `meta.json`，记录文件指纹与最近一次运行用的视觉配置。
缓存键 = base_url + 模型标识 + 提示词哈希 + scale 四项。

配置指纹**做成目录层级**而不只是 JSON 里的一个字段，是实测后（任务 2.6）改的：平铺时换模型
重跑会覆盖上一次的产物，换回来要重付 70 次调用（约 20 分钟）。而「比较哪个模型读得准」正是
把模型做成可配置的原因，这个来回恰是最该省下的花费。多出的磁盘占用只是文本，可忽略。

**被否决的替代方案**：沿用 `chunking.py:71` 的内存字典 `_EXTRACT_CACHE`。

**否决理由**：一次提取 = 19 分钟与真实 API 费用，重启即全部丢失。更关键的是本次实测到
通路本身会断（本机 LM Studio 被一张 1.57 MP 的图打崩过一次；云端中转抛
`ssl.SSLEOFError`，一次调用重试 4 次才成功）。没有落盘 checkpoint，一次中断就要从头再付一遍。

**代价**：多一个运行期目录要管理。真正的风险是**配置指纹写漏一项**——那样换了提示词却复用
旧产物，产出「看起来正常但属于旧配置」的文本，这是本设计里最隐蔽的一类失败。所以四项全部
写进 `meta.json`，并在预览里把当前指纹显示出来供人工核对。

### D5. 提取内存缓存的键纳入配置指纹

**选择**：`_extract_record()` 的缓存键由 `(绝对路径, mtime, 大小)` 扩为再带一个视觉配置指纹。

**被否决的替代方案**：不动这个键，靠 `preview_fingerprint` 的 `markdown_hash` 兜底。

**否决理由**：兜底不成立。`is_fresh()` 自己会调 `extract_markdown()`，而它会命中
`_EXTRACT_CACHE`（`chunking.py:158`）拿到**旧配置**的 T′——于是 `markdown_hash` 与旧预览的
相同，`is_fresh` 返回 True，使用者在改完模型后直接把一份用旧模型产出的文本入了库。
这条路径恰好穿过本设计最想避免的那个失败。

**代价**：缓存键变长；改任一 `VLM_*` 配置都会让内存缓存整体失效（这是正确行为，代价是重新
提取——而落盘缓存让重新提取只花读盘的时间，只要配置指纹本身也进了落盘键，即 D4）。

### D6. 视觉块用成对标记界定，并加入受保护区间

**选择**：每个视觉块写成自成一段的两行标记加正文：

```
[[VISION p35 图 2-7 收敛性能分析]]
横轴：训练轮次，刻度 0/100/200/300/400/500
纵轴：奖励，刻度 −5/0/5/10
图例：MLRA。走势：从 −5 起快速上升，约 200 轮后进入 8~10 的锯齿震荡
[[/VISION]]
```

块前后各留一个空行；`_protected_regions()` 增加一条规则识别这对标记之间的区间。

**被否决的替代方案**：不加标记，只靠空行让视觉块自成一段。

**否决理由**：`_protected_regions` 只被语义分割消费（Context 2），而语义分割正是会在块内部
按向量距离切断的那个切分器——不加标记，一段图的描述会被切成两半分别进两个 chunk。另外，
没有标记就无法在预览里指出哪些文字来自视觉，也就没有 D7 的对照呈现可依附的位置。

**代价**：标记字符进入 T′，计入覆盖率的分母，并被嵌入向量。选择成对 ASCII 标记而不是更漂亮
的排版，是因为它必须能被正则稳定识别，且在原文里不可能自然出现。

**实现期补记（实测，任务 2.3）**：模型**不会**稳定给出上面这种成对形态。第 31 页的真实
输出是开标记缺 `]]`、闭标记写成单独一行的 `]]`、后面还把题注重复了一遍。若原样放行，
`count_vision_blocks` 会对有图的那一页报 0，保护区间静默失效——描述会被切开且不报错。
所以「模型输出 → 规范形态」这一步是**必需的**，不是收尾美化：`normalize_vision_markers`
容忍全部观察到的变体并一律收敛成上面这一种，下游只认这一种。提示词也据此收紧了一句
（开标记与题注同行并以 `]]` 结尾，闭标记单独占一行），但这只是降低变体频率，不能替代规整。
因为提示词进了配置指纹，收紧提示词本身就换掉了指纹，旧缓存自动失效。

### D7. 失败显形：硬失败是判据，逐页对照只呈现

**选择**：三类结局逐页记录并在预览里计数——`ok`（解析成功）、`empty`（模型返回空串）、
`failed`（调用失败或超时）。预览另呈现每页的**转写字符数**与**同页文本层字符数**两个数。

**被否决的替代方案**：按两个字符数的比值设阈值，比值低于阈值自动标记「需人工确认」。

**否决理由**：以图为主的页面其文本层本就残缺——第 31 页的文本层是 `A gentn 、 ＇` /
`环境 Agent2` / `动作广 X −`，比值低属于正常现象。据其判定会对这类页面误报，而**误报会让
使用者不再相信这条信息**——这与会话前面已经确立的立场同源：主 spec
「提取质量在预览时可见」里禁止用 CJK 占比、表格行占比这类统计特征当告警判据，理由正是
「那类特征在检索正常的文档上同样可能很极端」。两个字符数的比值属于同一类。

**代价**：模型静默漏字不会被系统自动发现，只能靠使用者看那两个数。这是选缝法 B 时明确接受的
代价（D2），写在这里是为了让它保持可见，而不是被当成已经解决了。

### D8. 不自动回退到本机视觉模型；失败页回退到该页文本层

**选择**：云端调用失败时报失败，不改用本机视觉模型。单页失败时，该页正文取该页的文本层，
并在预览的状态计数里标为 `failed` 且说明其正文来源。

**被否决的替代方案**：云端不可用时自动切到本机模型继续。

**否决理由**：两者产出的文本不同（同一页本机 7B 与云端 235B 的转写逐字不同），静默切换等于
让知识库里混进两种口径的内容。这正是禁区 9 要挡的形态——失败被掩盖成成功。

**代价**：云端不可用时整份文档的视觉提取就停在那里。这是有意的：宁可停，不可混。

### D9. 页内文本层取自 `pypdfium2`；视觉开启时 PDF 不再走库的 markitdown 路径

**选择**：逐页对照与失败页回退用的「同页文本层」，取自 `pypdfium2` 的逐页 textpage。
视觉段启用且文件是 PDF 或图片时，不再调用 `_convert_via_library()`
（`chunking.py:100`，最终落到库的 `_convert_to_markdown`，`hello_agents/memory/rag/pipeline.py:49`）。

**被否决的替代方案**：继续调库拿平坦文本，只把它当对照。

**否决理由**：库的输出没有页界（Context 1），无法映射到页，既做不了逐页对照也做不了逐页回退。
继续调用它只会白付一次 markitdown 的解析时间，产出一份用不上的字符串。

**替代方案的备选（已否决）**：自己按页调两次提取再拼——`_convert_to_markdown` 不接受页码参数，
按页切分它就得先知道页界，回到同一个死结。

**代价**：PDF 的文本层读法从 pdfminer.six 换成 pypdfium2，两者输出不同（库那条还多一段
`_post_process_pdf_text`，`hello_agents/memory/rag/pipeline.py:103`，实测把 172590 字符压到
172500）。因为对照只呈现不判定（D7），这个差异只影响那两个数的可比性，不影响判定。
**这一点待实测**：见 Open Questions。

### D10. 独立图片文件走同一条视觉提取；未配置时明确失败

**选择**：`.png` / `.jpg` / `.jpeg` / `.bmp` / `.tiff` / `.tif` / `.webp` / `.gif`
（`chunking.py:92` 已在支持列表内）由视觉模块产出单块描述作为 T′。

**被否决的替代方案**：给 MarkItDown 的 ImageConverter 传 `llm_client`。

**否决理由**：库的 `_get_markitdown_instance()`（`hello_agents/memory/rag/pipeline.py:11`）
构造 `MarkItDown()` 时不传任何参数（**已实测确认**，读源码）。要给它传 `llm_client` 就得改库，
触禁区 1。

**行为变化**：未配置 `VLM_*` 时，上传图片文件**报错**并说明缺少哪项配置，而不是像现在这样
落到 `_convert_via_library` 的最后一层 `open(path, errors="ignore")`（`chunking.py:134`）
把 PNG 块结构解码成文本。这是有意的：那层兜底在图片上产出的是 95,741 字符的噪声，而覆盖率
与提取质量两项度量都显示正常——正是最该报错却最安静的一种失败。

**代价**：没配视觉模型的使用者上传图片会从「得到垃圾」变成「得到报错」。这是把一次静默劣化
换成一次显式失败，方向正确，但它确实是一次对外行为的变化，已写进 spec 的
「视觉提取不可用时明确失败」。

### D11. HTTP 客户端用 `openai` SDK，指向 OpenAI 兼容端点

**选择**：`openai` SDK，`base_url` 与 `api_key` 取自 `.env` 的 `VLM_BASE_URL` / `VLM_API_KEY`。

**被否决的替代方案**：手写 `urllib.request`（本次探索期的试探脚本就是这么写的）。

**否决理由**：超时、重试、连接复用都要自己实现，而本次实测里三类通路故障都真实出现过——
本机服务被大图打崩（`RemoteDisconnected`，随后 `WinError 10061` 连接被拒）、云端中转
`ssl.SSLEOFError`、单次调用前三次 `URLError` 失败。重试与退避是**必需功能**而不是健壮性装饰。
`openai` 1.109.1 本机已装（**已实测确认**），不新增依赖。

**代价**：引入 SDK 自身的超时与重试语义，需要显式配置以免与 D4 的逐页 checkpoint 语义冲突
（重试要在页这一层做，不要在整份文档那层做）。

## 本次不能破坏的既有契约

逐条指回主 spec 的 requirement：

| 既有契约（requirement 名） | 为什么不会被破坏 |
|---|---|
| 预览与入库结果一致 | T′ 在 `_extract_record`（唯一入口）内产出，预览与入库消费同一份 `Workbench.materialized` |
| 入库 chunk 保持可检索（位置为真实偏移） | T′ 是真实字符串，偏移是 T′ 内的真实字符偏移 |
| 切分不丢内容（覆盖率用位置区间并集） | 公式不变，只是分母从「库提取文本长度」变成 `len(T′)`。新增好处：某个视觉块没落进任何 chunk 会显现为覆盖率缺口，而不是悄悄消失 |
| 参数变化后预览失效 | 由构造保持——`preview_fingerprint` 含 `markdown_hash`（`chunking.py:1476`），`is_fresh` 重新提取再比（`chunking.py:1709`）。**前提是 D4 与 D5 都做对**，否则 T′ 不随配置变化，这条契约会静默失效 |
| 提取文本的确定性清洗 | 本次以 MODIFIED 扩展其作用域（视觉转写同过一条清洗），确定性改由落盘缓存承接 |
| 提取质量在预览时可见 | 判据仍是私用区与全角拉丁两类编码噪声；新增的字符数对照按 D7 只呈现、不判定，不新增判据 |
| 提交入库时清理旧切分（只作用当前文档） | 视觉提取全程不写知识库，重入库路径 untouched |
| 禁区 6（不动既有知识库数据） | 预览不写库；验证写入只用 `docs_qualitycheck` 并在事后清理 |

## Risks / Trade-offs

按失效形态排列，**静默劣化排在最前**。

1. **[静默劣化] 模型漏字，整段内容从知识库消失，且看不出来。** → 缓解：逐页呈现转写字符数
   与文本层字符数（D7）。**残留风险**：使用者不看就发现不了。这不会被消除，只能被保持可见。
2. **[静默劣化] 配置指纹漏写一项，换了提示词却复用旧产物。** → 缓解：四项全部写进
   `meta.json`，预览显示当前指纹（D4）。
3. **[静默劣化] 视觉块被语义分割从内部切断。** → 缓解：`_protected_regions` 增加识别规则
   与 `_iter_atoms` 的原子化（D6）。验证方式：对同一份文档分别用三种策略切分，断言每个
   `[[VISION …]]` 与 `[[/VISION]]` 落在同一个 chunk 内（超长块除外）。
4. **[静默劣化] `_EXTRACT_CACHE` 复用旧配置的 T′，`is_fresh` 误判为有效。** → 缓解：D5。
   验证方式：改 `VLM_MODEL_ID` 后重新提取，断言 `markdown_hash` 变化。
5. **[报错] 云端端点不可达 / SSL EOF / 连接被拒。** → 缓解：逐页重试 + 指数退避；逐页
   checkpoint 让重试不必从头付一次；失败页计入状态并按 D8 回退到该页文本层。
6. **[报错] 单页超时。** → 同上。超时值待实测，见 Open Questions。
7. **[静默劣化] 渲染失败（损坏的页、加密页）。** → 缓解：该页计入 `failed` 并在预览中说明
   其正文取自文本层，不伪装成解析成功。
8. **[报错] 落盘缓存目录不可写。** → 缓解：明确报错。**MUST NOT** 静默退化为「不缓存」——
   那会让每次重复预览都重付一次 API 费用，而使用者以为命中了缓存。

## Migration Plan

- **配置**：`.env` 的三项 `VLM_*` 已写入（本变更之前）。三项缺任一项时视觉段整体不启用，
  提取行为与本次变更前逐字相同——**图片文件除外**，见 D10。
- **存量数据**：不迁移、不重切、不自动重入库（禁区 6）。使用者重新预览并在预览中确认后，
  新参数才生效。
- **验证用命名空间**：`docs_qualitycheck`，验证后清理并断言回到 0 块。`docs_yyh` 只读核对。
- **回滚**：删除视觉缓存目录，还原 `chunking.py` 与 `11_Q&A_Assistant.py`。已入库的 chunk
  不受影响——它们只是文本，与产出它们的路径无关；但它们会继续以视觉提取的文本存在，
  回滚不会把它们变回去，需要重新入库才会。

## Open Questions

1. **单页超时取多少。** 待实测：235B 单页 16.5–18.1 s、flash 9.6 s，需要在「不误杀慢页」与
   「不把一次中断拖成一小时」之间取值。量出来之前不写一个看起来合理的数。
2. **`pypdfium2` 逐页文本与库输出（pdfminer.six + `_post_process_pdf_text`）的质量差多少。**
   它决定 D7 那两个数有多可比。不影响 spec、方案与任务划分——即使差很多，处置方式也是
   「呈现差异」而不是「改用另一条读法」。
3. **AIHubMix 的实际计费单价未核实**（只知约 73K 输入 token / 70 页文档）。只影响成本预期，
   不影响设计。
