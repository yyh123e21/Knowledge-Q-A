# Proposal

## Why

上传文件里图片上的信息从来没有进入过知识库；而当图片本身被当成正文读进来时，进来的是二进制噪声。

三份实测记录（本机，2026-09-24）：

1. **独立图片文件被当二进制读。** 把一张截图 `测试上传图片.png` 上传到「🔪 切分工作台」，段落分割、
   块大小 800 token、重叠 80：产出 10 个 chunk、95,741 字符、覆盖率 100.00%。chunk 1 的开头是
   `IHDR`、`pHYs`、`tEXtSoftwareSnipaste`、`IDAT`——PNG 的块结构被 `errors="ignore"` 解码成了文本。
   整份「正文」里没有一个字是图片的内容，而覆盖率与提取质量两项度量都显示正常。

2. **PDF 里的图在文本层中不存在。** 《低轨巨型星座网络智能路由技术研究_封思敏.pdf》经
   `extract_markdown()` 得到 163,545 字符，其中换页符 0 个、HTML 注释 0 个、页码标记 0 个。
   第 35 页的「图 2-7 收敛性能分析」（横轴训练轮次 0–500，纵轴奖励 −5~10，单条 MLRA 曲线）
   在文本层里一个字都没有；第 31 页「图 2-5 MLRA 算法框架图」的题注被拆成
   `MLRA 算法框架如图` / `2－5 。`，图内标签变成 `A gentn 、 ＇` / `环境 Agent2` / `动作广 X —`；
   同页的「续表 2-3 算法参数」（贪婪度 ε [0.001,0.99]、学习率 α 0.001、经验池容量 2000、
   batch 32、ReLU 激活）被压成只剩边框。

3. **文本层本身也带损伤。** 同一份 PDF 的文本层含私用区字符 ``、``、``
   （正是 `QUALITY_PUA_RATIO_LIMIT = 0.001` 针对的噪声）；标题「2.2.2 算法实现」被拆成
   `２ ２ ２`、`算法实现`、`． ．` 三段。

把同一页整页渲染后交给 `qwen3-vl-235b-a22b-instruct` 转写，结果严格优于上面的文本层：标题、标点、
公式 (2-28) 全部正确，无私用区字符。图上的信息同样是可读的——第 35 页图 2-7 的描述（坐标轴名称与
刻度、图例、曲线走势）经逐条比对渲染页，无一处编造，且模型主动声明其余数值不可精确读出。

这一步在本机 CPU 上跑不动：实测 140 s/百万像素且线性，70 页要 1.4–6 小时。换云端后单页
scale=1.5（819×1243，1.02 MP）耗时 16.5–18.1 s，70 页约 19 分钟，代价可接受。

需要说明的是，`pypdf` 抽出的嵌入图**是水平镜像的**（`.images[i].image` 不含 PDF 的放置变换矩阵，
实测第 31 页 1823×860 的插图与第 50 页的框图文字全反）。本变更不使用这条路径。

## What Changes

- **新增 `vision.py`**：整页渲染 + VLM 调用 + 逐页落盘缓存 + 逐页状态。不 import `11_Q&A_Assistant.py`，
  不含切分逻辑，只提供「文件 -> 每页的视觉文本与状态」。
- **`chunking.py::_extract_record()` 插入视觉段**。它是现有的唯一提取入口，`preview` / `index` /
  `is_fresh` 三个调用点自动全覆盖。PDF 逐页渲染并转写，把每页的「转写 + 图解读」拼成新的提取文本
  `T′`；独立图片文件走单图路径。清洗、质量度量、切分、覆盖率全部照旧消费 `T′`，不新增第二条路径。
- **`chunking.py::_protected_regions()` 增加第四类受保护区间**：视觉描述块与现有的围栏代码块、
  连续表格行一样整体保留，不被切分器从中间切开。
- **`chunking.py` 增加视觉缓存目录**：以「文件指纹 + 视觉配置指纹（base_url + 模型 + 提示词 + scale）」
  为键，每页一个文件落盘。改配置即视为一次新提取，不复用旧配置的产物；中断后重跑只补缺失的页。
- **`11_Q&A_Assistant.py::preview_chunks()` 的状态串增加视觉解析摘要**：逐页成功/空/失败计数与失败页
  页码，按现有 `viz.summarize_*` 的写法接进 `notes`。
- **`.env` 增加 `VLM_BASE_URL` / `VLM_MODEL_ID` / `VLM_API_KEY`**（本变更之前已按使用者要求写入；
  其值不出现在任何输出、日志或 artifact 中）。

可判定的结果：

- 上传一份含图表的 PDF 并预览，chunk 里出现该图的文字描述；就图中内容提问能命中该 chunk。
- 上传一张独立图片文件并预览，chunk 里出现该图的文字描述，而不是 `IHDR` / `IDAT` 之类的二进制。
- 视觉解析失败的页在预览里显形为逐页计数（成功 / 空 / 失败），且系统在这种情况下不报告成功。
- 换 `VLM_MODEL_ID` 后重新预览，视觉文本随之改变，不复用上一配置的缓存产物。

## Capabilities

### New Capabilities

- `visual-content-ingestion`: 用视觉模型把文档里的图片与图表的可读信息提取成文字、与正文一并进入
  切分与知识库；并保证提取过程的失败可见、结果可复现、过程可续跑。

### Modified Capabilities

- `document-chunking`: 「提取文本的确定性清洗」——视觉转写纳入这条清洗的作用域，其确定性改由落盘
  缓存保证，因为模型输出本身不是确定的。

## Non-goals

1. **不改清洗规则本身。** 视觉转写与正文过同一条清洗，仍是禁区 4 的三类定点改动，不新增第四类，
   也不用 `NFKC`。理由：视觉转写会引入空格与全角字符，但那正是现有清洗已覆盖的两类；再开规则
   等于把「提取质量」这条已经收口的线重新拉开。
2. **不给 `.docx` / `.txt` / `.md` / `.csv` 等文本格式加视觉段。** 理由：它们没有「整页」这个概念，
   渲染的落点不存在，硬做只能退化成分页截图，收益与成本都不成立。
3. **不做版面分析与目标检测**（识别一页里有几个子图、图注归属、阅读顺序）。理由：整页渲染交给
   VLM 的实测结果已经够用（第 35 页的描述经逐条比对无编造）；版面分析是另一个量级的工作，
   且会引入检出失败这一新的失败类别。
4. **不迁移、不重切、不自动重新入库任何存量 chunk**（禁区 6）。视觉提取只在使用者重新预览并在
   预览中确认后生效。理由：知识库里的内容是真实使用数据，自动重切会让偏移与切分来源无预警地变化。
5. **不修 `pypdf` 嵌入图镜像的路线。** 理由：已实测该路径丢失放置变换矩阵，产出镜像图，
   修它需要在应用层重实现 PDF 的变换矩阵，而整页渲染天然没有这个问题，收益为负。
6. **不引入第三方切分或提取框架**（禁区 8）。`pypdfium2` 与 `openai` 都不新增——实测本机已有
   （`markitdown → pdfplumber → pypdfium2` 5.8.0；`openai` 1.109.1）。
7. **不把云端调用失败自动回退到本机视觉模型。** 理由：两者产出的文本不同，静默回退等于让知识库里
   混进两种口径的内容（禁区 9）。

## Impact

- **新增文件**：`vision.py`。**修改文件**：`chunking.py`、`11_Q&A_Assistant.py`。`chunk_viz.py` 不改
  （它只渲染传入的度量，渲染契约不变）。
- **依赖**：不新增第三方包。`pypdfium2` 与 `openai` 本机已装，且都不是切分或提取框架。
- **配置**：`.env` 新增三项 `VLM_*`。未配置时视觉段整体不启用，提取行为与本次变更前完全一致。
- **运行期数据**：新增一个落盘缓存目录（每页一个 JSON 文件）。不写知识库；不触碰 `docs_yyh`，
  也不触碰 `default` 命名空间的存量数据。
- **成本**：视觉解析按页调用外部 API，按量计费。单份 70 页文档约 73K 输入 token
  （实测 ptok≈1052/页，scale=1.5）。
- **既有行为**：PDF 与图片文件的提取文本来源改变，其字节级内容与从前不同。文本格式的提取路径
  完全不变。
